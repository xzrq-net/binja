# Decide queue depth and busy semantics from observed agent usage

The primary client is GPT through Codex. Rather than pick a backlog policy up
front, keep the current queue (cap 64 pending, serial worker) through the
simplification in `vtw63f` and the usability trials in `2nbgtk`, then read the
revealed preferences: how often an agent submits while work is running, whether
it issues parallel commands, and how it reacts to waits versus errors.

Candidates on the table:

- Small queue (4 to 8) that serializes parallel tool calls silently; the cap only
  flags runaway loops.
- No backlog: an explicit busy response naming the running request ID, with
  reconnect/wait against it.

Record the observations and the decision in the investigation log.

Related ergonomics question for the same observation window: `binja requests`
now lists every record for the session lifetime, since metadata is no longer
evicted. Decide whether the listing should default to pending plus the newest
few finished requests.

## Observations from the first usability trials

Recorded in the investigation log under "First usability trials with GPT".
Summary: across 18 session-bound requests in three single-client sessions, no
submit-while-running occurred; parallelism was limited to session-less `api`
lookups and status inspection during a 42 s analysis. All three subjects said
they would prefer queueing with an explicit "queued" receipt (target, what it
waits behind, cancel) over a busy error, and would accept a busy error only if
it clearly means "not accepted, will not execute". All three want `requests`
to lead with running/queued entries (ID, target, phase, elapsed) and to limit
or filter completed history. Two-client contention on one session was not
exercised.

Closed: Retained the serial queue with a cap of 8 unfinished requests, explicit queued receipts and safe rejection, and pending plus five newest finished entries by default (--all for history). Decision and live smoke evidence recorded in docs/log.md.
